## Q1. How well the designs shows the entities?

**Score:** ⭐ 9.0/10

**Strengths:** Your design demonstrates excellent entity modeling with clear, well-defined classes that accurately represent the TicTacToe game domain: 

1. **Core Game Entities**: You've identified and implemented all essential entities - `Game`, `Board`, `Cell`, `Player`, `Move`, and `Symbol`. Each class has a clear purpose and appropriate attributes. For example, the `Cell` class properly encapsulates row, col, cellState, and player, which are all necessary attributes for representing a board position. 

2. **Player Hierarchy**: The player modeling is particularly well done with a base `Player` class and specialized `HumanPlayer` and `BotPlayer` subclasses. The `BotPlayer` class correctly includes bot-specific attributes like `botDifficultyLevel` and `botPlayingStrategy`, showing good understanding of entity specialization. 

3. **Strategy Entities**: You've properly identified strategies as separate entities with `WinningStrategy` interface and its implementations (`RowWinningStrategy`, `ColumnWinningStrategy`, `DiagonalWinningStrategy`), as well as `BotPlayingStrategy` with its difficulty-based implementations. This shows excellent recognition of behavioral entities. 

4. **Supporting Entities**: The inclusion of enums (`GameState`, `CellState`, `PlayerType`, `BotDifficultyLevel`) demonstrates good design judgment in using appropriate types for state management. 

5. **Controller and Service Layer**: You've correctly identified the need for separation between presentation (`GameController`) and business logic (`GameService`), showing understanding of architectural entities. 

**Areas for Improvement:** 
1. **Missing Undo/History Entity**: While you have `undoMove` method in `GameService`, it's not implemented. A dedicated `GameHistory` or `MoveHistory` entity could better represent the concept of game history management. Currently, the `List moves` in `Game` serves this purpose but lacks encapsulation. 
2. **Symbol Validation Entity**: There's no dedicated entity for symbol validation or symbol management. While you have validation in the `Game.Builder`, a `SymbolValidator` or `GameRules` entity could better represent game constraints. **Actionable Suggestions:** 
1. **Add a GameHistory entity** to better encapsulate move management: ```java public class GameHistory { private Stack moves; public GameHistory() { this.moves = new Stack<>(); } public void addMove(Move move) { moves.push(move); } public Move undoLastMove() { if (!moves.isEmpty()) { return moves.pop(); } return null; } public Move getLastMove() { return moves.isEmpty() ? null : moves.peek(); } public int getTotalMoves() { return moves.size(); } public List getAllMoves() { return new ArrayList<>(moves); } } ``` **Why this is better**: This encapsulates move history management, making it easier to implement undo/redo functionality and providing a single point of control for move-related operations. It follows the Single Responsibility Principle by giving the Game class one less concern to manage. 
2. **Consider a GameRules entity** to encapsulate game validation logic: ```java public class GameRules { private int boardSize; public GameRules(int boardSize) { this.boardSize = boardSize; } public void validatePlayers(List players) throws InvalidGameException { validatePlayerCount(players); validateUniqueSymbols(players); validateBotCount(players); } private void validatePlayerCount(List players) throws InvalidGameException { if (players.size() != boardSize - 1) { throw new InvalidGameException( "Player count must be " + (boardSize - 1) + " for a " + boardSize + "x" + boardSize + " board." ); } } private void validateUniqueSymbols(List players) throws InvalidGameException { Set symbols = new HashSet<>(); for (Player player : players) { char symbol = player.getSymbol().getCharacter(); if (symbols.contains(symbol)) { throw new InvalidGameException("Duplicate symbol found: " + symbol); } symbols.add(symbol); } } private void validateBotCount(List players) throws InvalidGameException { long botCount = players.stream() .filter(p -> p.getPlayerType() == PlayerType.BOT) .count(); if (botCount > 1) { throw new InvalidGameException("At most 1 bot is allowed per game."); } } } ``` **Why this is better**: This creates a dedicated entity for game rules and validation logic, making it reusable and testable independently. It also makes the Game.Builder cleaner and follows the Single Responsibility Principle. If you need to add more rules (e.g., minimum board size, valid symbols), you have a clear place to put them.

## Q3. How well the designs follow SOLID principles?

**Score:** ⭐ 8.0/10

**Strengths:** 
1. **Single Responsibility Principle (SRP)**: Your design demonstrates good SRP adherence in many areas: - `Cell` class is responsible only for maintaining cell state - `Symbol` class encapsulates only symbol data - `Move` class represents only a single move - `Board` handles only board state and display - `GameController` acts solely as a facade for UI interactions - `GameService` contains only game logic 
2. **Open/Closed Principle (OCP)**: Excellent implementation through strategy patterns: - `WinningStrategy` interface with multiple implementations (`RowWinningStrategy`, `ColumnWinningStrategy`, `DiagonalWinningStrategy`) allows adding new winning conditions without modifying existing code - `BotPlayingStrategy` interface enables adding new bot difficulties without changing existing implementations - This is one of the strongest aspects of your design 
3. **Liskov Substitution Principle (LSP)**: Your inheritance hierarchy respects LSP: - `HumanPlayer` and `BotPlayer` can be substituted for `Player` without breaking functionality - All strategy implementations can be used interchangeably through their interfaces 
4. **Interface Segregation Principle (ISP)**: Your interfaces are well-focused: - `WinningStrategy` has a single, focused method - `BotPlayingStrategy` has a single, focused method - No interface forces clients to depend on methods they don't use 
5. **Dependency Inversion Principle (DIP)**: Good use in some areas: - `BotPlayer` depends on the `BotPlayingStrategy` interface rather than concrete implementations - `Game` depends on `WinningStrategy` interface rather than concrete implementations - `GameController` depends on `GameService` abstraction **Areas for Improvement:** 
1. **SRP Violation in Main Method**: The `TicTacToeGame.main()` method has multiple responsibilities: - Game initialization - User input handling - Move validation - Game loop management - Output display - Player type switching logic This is a significant SRP violation that makes the code difficult to test and maintain. 
2. **SRP Violation in Game.Builder**: The `Builder` class is doing both building AND validation. While this is common, separating validation into a dedicated validator class would be cleaner and more testable. 
3. **DIP Violation in GameController**: `GameController` depends directly on the concrete `GameService` class rather than an interface. This makes it difficult to mock for testing or swap implementations. 
4. **God Object Tendency in Game Class**: The `Game` class, while not terrible, is starting to become a god object with many responsibilities: - Managing board state - Managing players - Managing moves history - Managing game state - Managing winner - Managing strategies - Managing next player logic 
5. **Missing Abstraction for Player Input**: The main method directly handles player input logic with type checking (`if (currentPlayer.getPlayerType() == PlayerType.BOT)`). This violates the Open/Closed Principle because adding a new player type requires modifying this code. **Actionable Suggestions:** 
1. **Refactor Main Method** to follow SRP: ```java public class GameOrchestrator { private Game game; private GameController controller; private GameView view; private InputValidator inputValidator; public GameOrchestrator(Game game, GameController controller, GameView view) { this.game = game; this.controller = controller; this.view = view; this.inputValidator = new InputValidator(game.getBoard().getSize()); } public void startGame() { view.displayMessage("==== TicTacToe ===="); while (controller.getGameState(game) == GameState.IN_PROGRESS) { playTurn(); } displayGameResult(); } private void playTurn() { controller.printBoard(game); Player currentPlayer = getCurrentPlayer(); Move move = getMoveFromPlayer(currentPlayer); if (move != null && inputValidator.isValidMove(move, game.getBoard())) { controller.makeMove(game, move.getCell(), move.getPlayer()); } else { view.displayMessage("Invalid move. ## Q4. How well the design is using Interfaces, Abstract classes correctly ?

**Score:** ⭐ 8.0/10

**Strengths:** 
1. **Excellent Interface Usage for Strategies**: Your use of interfaces for strategy patterns is exemplary: - `WinningStrategy` interface with method `boolean checkWinner(Board board, Move lastMove)` is perfectly designed for the Strategy pattern - `BotPlayingStrategy` interface with method `Move getMove(Board board, Player player)` allows for polymorphic bot behavior - These interfaces define clear contracts and enable easy extension 
2. **Proper Interface Implementation**: All strategy implementations correctly implement their respective interfaces: - `RowWinningStrategy`, `ColumnWinningStrategy`, `DiagonalWinningStrategy` all properly implement `WinningStrategy` - `EasyBotPlayingStrategy`, `MediumBotPlayingStrategy`, `HardBotPlayingStrategy` all implement `BotPlayingStrategy` 
3. **Good Inheritance Hierarchy**: The `Player` class serves as a good base class with `HumanPlayer` and `BotPlayer` extending it appropriately. Each subclass adds specific functionality while maintaining the base class contract. 
4. **Strategy Factory Pattern**: The `BotPlayingStrategyFactory` effectively uses the factory pattern with interfaces, making bot strategy creation clean and maintainable. **Areas for Improvement:** 
1. **Player Class Should Be Abstract**: The `Player` class is currently a concrete class but it's only used as a base for `HumanPlayer` and `BotPlayer`. It should be abstract since a generic "Player" without a specific type doesn't make semantic sense in your domain. More importantly, if you add behavior that differs between player types (like the `getMove()` suggestion in SOLID feedback), an abstract class would enforce that subclasses implement their own behavior.

5. **No Common Exception Interface**: While you have `InvalidGameException`, having a common interface or base class for game-related exceptions would help with exception handling and make the design more cohesive.

1. **Board-Cell Relationship Could Be Stronger Composition**: The `Board` creates and owns cells, which is composition, but cells could be made more explicitly dependent on their board. Currently, a `Cell` object could theoretically exist without a board, which doesn't make semantic sense. 
2. **Missing Bidirectional Relationship**: `Cell` has a reference to `Player` when filled, but there's no easy way to find all cells a player has marked without iterating through the entire board. For certain game features (like highlighting a player's moves), a bidirectional relationship or a separate tracking mechanism would be beneficial. 
3. **Move-Cell Relationship is Ambiguous**: `Move` has a composition relationship with `Cell`, but it's not clear if the Move owns the cell or just references it. In reality, it should be an association (reference) since the Cell exists independently in the Board. 
4. **Game-Winner Relationship**: The `winner` field in `Game` is typed as `Player`, but this is actually a reference to an existing player in the `players` list, making it an association rather than composition. This is correct, but could be clearer with documentation. 
5. **GameController-Game Relationship**: The controller receives `Game` as a parameter to each method but doesn't store it. This is a dependency relationship, but the design might benefit from the controller managing a single game instance through composition.
